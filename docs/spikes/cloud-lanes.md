# Lanes and checks on cloud machines

Started on 2026-11-20 with Claude Code 2.1.310 and the Sprite CLI 2026-11-03, on a Mac Studio (M3 Ultra, 28 cores, 96 GB) running several code-kit projects at once. The spike has to answer three things: whether moving work to cloud machines would relieve that Mac, which platform fits (Fly's Sprites or Daytona), and whether the feature belongs in the hub.

The platform and Claude Code facts below were read from the official docs on 2026-11-20. The Mac was measured. One Sprite was created and tested the same day, and [Tests on a Sprite](#tests-on-a-sprite) has what ran. The first feature it describes is specified in `docs/specs/32-checks-on-a-runner.md`.

## What loads the Mac

One sample, taken at 10:52 with several projects building:

| Measure                                   | Reading                                                          |
| ----------------------------------------- | ---------------------------------------------------------------- |
| Load average (1, 5 and 15 minutes)        | 32, 30 and 35, on 28 cores                                       |
| Memory free                               | 29% of 96 GB                                                     |
| The 12 `claude` processes together        | 0.8 of a core, 5.9 GB                                            |
| The 64 `node` processes together          | about 6 cores, 6.3 GB                                            |
| The 32 `python` processes together        | about 7.5 cores, 2.0 GB                                          |
| A local virtual machine                   | about 2 cores                                                    |
| Headless Chromium (Playwright)            | about 1.6 cores                                                  |
| The merge queue's checks, in two projects | A Python test run and a Playwright run, both running at the time |

The Mac is short of cores, and has memory to spare. The Claude sessions use under a core between them; the load is what they run: simulations, test suites, browser tests, and the merge queue's own checks of each merged tree. So the thing to move is the commands. Moving a lane's whole session moves its commands with it, and the queue's checks can move without any session at all.

This is one sample. It should be taken again across a working day before any number here is used to size something.

## What a Sprite and a Daytona sandbox cost

Prices are the published ones, in US dollars. The arithmetic is for one machine of 8 vCPU and 16 GB with 20 GB of disk, working 4 hours a day for 30 days.

| Platform         | Rates                                                         | Flat out for the 120 hours | At Fly's coding-session average (0.6 CPU, 1.5 GB) | Idle all month |
| ---------------- | ------------------------------------------------------------- | -------------------------- | ------------------------------------------------- | -------------- |
| Sprites          | $0.0385 a CPU-hour and $0.021875 a GB-hour, on actual use     | about $81                  | about $9                                          | about $0.40    |
| Daytona 2.0      | $0.101 a core-hour (2 vCPU) and $0.0162 a GiB-hour, on demand | about $81                  | The same $81: it bills what's reserved            | The volume     |
| Daytona, earlier | $0.0504 a vCPU-hour and $0.0162 a GiB-hour                    | about $81 (over its cap)   | The same                                          | Disk only      |

A lane's session is idle most of the time it's open, waiting on the model, so billing on actual use is what makes a Sprite per lane affordable. A test run that pegs 8 cores for ten minutes costs about 5 cents of CPU on a Sprite.

### What an idle Sprite costs

A Sprite with nothing open goes to sleep and bills storage only: 3.4 GB of checkout, installs and plugin on this one, which is about 7 cents a month at the cold rate.

A Sprite with something left open stays awake and bills. A console session with `claude` sitting at its prompt held this one awake for the 37 minutes it was watched, with no gap in its uptime. Over ten of those minutes, untouched, it used 0.02 of a core, which is under the 0.0625 CPU that a running Sprite is billed at least, and held 0.9 GB of memory, most of it file cache.

| What memory is billed on                     | An hour awake and idle | A day | A month |
| -------------------------------------------- | ---------------------- | ----- | ------- |
| Memory in use (0.9 GB), as the pricing reads | about $0.025           | $0.60 | $18     |
| Memory reserved (the policy's 8 GB)          | about $0.18            | $4.30 | $129    |

Which row is right isn't known yet. The pricing page says memory is billed on actual use. The usage API (`GET /v1/usage/<sprite>`) counts `reserved_memory_byte_sec`, the Sprite's policy reserves 8 GB with autoscaling off, and the API still returned zeros five and a half hours after the Sprite was created. The figure has to be read from that API, and from the invoice, after a day in known states: asleep, held awake by an idle session, and working.

Either way the design has to stop a Sprite being left awake. A lane's session should be a headless one that ends when its story is handed back, so the Sprite sleeps by itself; nobody should need a console left open; and whatever starts Sprites should show which are awake, for how long and what holds them, beside the cost register.

Moving sessions to cloud machines adds no Claude usage. Every lane still draws on the person's one subscription, wherever it runs.

## What changes in the design

There are two features here, and the first is much the smaller.

The first is a runner for checks. The merge queue's verify of a merged tree, and the fix check's, run commands in a fresh checkout and read the result. A runner does the same on another machine: get the tree there, run the install where the lockfiles changed, run the checks, bring back the exit status and the output. It needs no Claude sign-in, so none of assumption C's limits apply, and it takes away load the Mac carries today for every merge in every project. The core gets one seam, as the team provider has: checks run `local`, or through a command, with each platform as an adapter under `hooks/lib/adapters/`, since the core never names another tool.

The second is a lane on a cloud machine. Because of B, this is a working session in the VM, started in the project's checkout there, on its lane's branch. The VM keeps the lane's worktree and installs between stories, which is LEAN-10 on another machine and why a Sprite's persistent disk suits it. The lane pushes its branch; the lead fetches it and queues it as it does a teammate's.

The tests fixed four things about how that session is started.

- It's `claude --agent <the lane's agent>` on the lane's branch. code-kit's hooks then hold it to the lane's paths as they hold a sub-agent, so the rules need no second form for cloud lanes.
- It runs with Claude Code's own permission prompts off. With them on, Claude Code refused the lane's report under `.claude/state/` in a headless session, and the finish check asked for it three times and gave up. With them off, the report was written and code-kit still refused the write the lane wasn't allowed. The README says the hooks are guard rails and not a sandbox; on a runner, the VM is the sandbox.
- It's recorded as a working session. code-kit recorded the lane's session on the Sprite as the lead, because it was the only session in that checkout, and a checkout on a runner must never hold the lead.
- It's started as something that outlives whoever started it. A command run with `sprite exec` was killed when the caller disconnected, so a lane started that way from a laptop stops when the laptop sleeps. Sprites have services and detachable terminal sessions for this, and the hub's companion on the Sprite would be the one starting sessions in any case.

The hub is the right home for the second, and a reasonable one for the first, for three reasons. It already runs in Fly, and Sprites belong to the same organisation and bill. Its companion is installed once per computer and starts and answers Claude sessions there, so a Sprite with the companion on it is one more of the person's computers, and what the assistant can do on the Mac it could do on the Sprite with nothing new. And the hub is a GitHub App, so it can give a Sprite a short-lived token for one repository instead of a person's `gh` sign-in. Test 7 shows why that's worth having: the `gh` sign-in works, and leaves a token for every repository the person has on the Sprite's disk. It needs the App to hold write access to repository contents, which it may not have today and which each organisation would have to approve. Sprites' own GitHub connector keeps the token off the Sprite too, but it forwards calls to GitHub's API and the docs show nothing for `git push` through it; it wasn't set up or tried. The hub's code is outside this repository and wasn't read for this spike, so the companion's part is from its spec and needs checking there.

What the hub must not do is touch the Claude sign-in. The person signs in to Claude inside their Sprite once, in its console, and the credential stays on the Sprite's disk. A design in which the hub stores a token and hands it to machines is the one Anthropic's terms rule out.

Three pieces of state have to cross machines for a cloud lane, and each has an existing carrier to extend before anything new is built.

- The lane's claim (SCHED-1) is a file on the lead's machine. A lane running elsewhere has to hold the same claim, so it goes through the team provider beside the story's claim.
- A decision the lane needs from the person (spec 15) is a file too. The hub's liaison already carries questions and approvals between a session and the person's assistant.
- The event log stays where it is. DUR-2 keeps it local and out of every report, and the hand-over brief is built on the machine that holds the lane's worktree, which is now the Sprite.

Spec 29's cost register gets a line for each runner, read against the budget as any other environment is.

The tests added three things a runner's setup has to do, whichever feature it serves.

- Clear the machine's global git ignore. A Sprite's image ships one that ignores `.env.*`, `build/`, `dist/`, `target/` and `*.log`, so a project's `.env.example`, or a source folder named `build`, would be left out of a commit made there with nothing said.
- Set the person's git name and email. A commit made on a Sprite is otherwise authored by `Sprite <noreply@sprites.dev>`.
- Expect a check to behave differently there. Two of code-kit's own mod tests, which passed for the 0.39.0 release, run past their 5-second limit on a Sprite. Its cores or its newer Claude Code (2.1.319, against 2.1.310 on the Mac) could each be the cause, and either way a check that passes on one machine can fail on the other. A project's checks have to run in one place, the runner, for the queue's answer to mean the same thing each time.

## What would make this the wrong call

- A project whose tests need Docker with published ports. Sprites can't run it, and such a project would need Daytona or a plain Fly Machine as its runner.
- A Sprite that sleeps under a session waiting on the model. Fly's pages disagree on whether a detached session holds it awake, and the tests settled half of it: an open console session does. Whether a lane's session started as a service does, while it waits on the model, still has to be tried with nothing else open on the Sprite.
- Memory and speed. The Sprite tested had 16 GB and 8 cores, and its cores looked slower than the Mac's on code-kit's mod tests. A project whose suite needs more of either has to run its checks somewhere else.
- A second sample of the Mac showing memory or disk, and not cores, as the limit.
